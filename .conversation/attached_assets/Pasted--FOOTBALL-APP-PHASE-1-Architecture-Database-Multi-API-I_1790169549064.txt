# FOOTBALL APP — PHASE 1

## Architecture, Database, Multi-API Integration System and Foundation

Build the foundation of a production-ready football live-score platform.

The application will eventually support multiple football APIs, news APIs, RSS feeds and statistics providers.

IMPORTANT:

Do NOT build the entire application at once.

This phase is ONLY for building the correct architecture and foundation so that all future APIs and features can be added without rewriting the application.

The application must use an original design and must not copy proprietary branding, assets or exact UI layouts from FotMob, SofaScore or Flashscore.

---

# 1. TECHNOLOGY STACK

Use:

* Next.js
* TypeScript
* React
* Tailwind CSS
* PostgreSQL
* Prisma ORM
* REST API architecture
* Redis or an equivalent cache if available
* Secure environment variables
* Responsive mobile-first UI

Use clean modular architecture.

---

# 2. CORE ARCHITECTURE

The architecture must be:

Frontend
↓
Our Backend API
↓
Data Integration Layer
↓
Provider Adapters
↓
External APIs
↓
Database + Cache

The frontend MUST NOT directly call external football APIs.

All external API communication must happen through our backend.

The frontend must only consume our own unified API.

---

# 3. MULTI-PROVIDER ARCHITECTURE

Create a provider abstraction system.

The application must NEVER depend directly on one API provider.

Create a structure similar to:

```text
/providers
    /football
        /thesportsdb
        /football-data
        /openligadb
        /api-football
    /news
        /gnews
        /newsdata
        /rss
    /video
        /scorebat
```

Not every provider needs to be activated immediately.

Create the architecture so providers can be enabled later.

---

# 4. PROVIDER INTERFACE

Create standardized interfaces.

For example:

```typescript
interface FootballDataProvider {
  getMatches(date: string): Promise<Match[]>;
  getMatchDetails(matchId: string): Promise<MatchDetails | null>;
  getLineups(matchId: string): Promise<Lineup[]>;
  getStandings(leagueId: string, season?: string): Promise<Standing[]>;
  getTeams(leagueId: string): Promise<Team[]>;
  getPlayers(teamId: string): Promise<Player[]>;
  getPlayerStats(playerId: string): Promise<PlayerStats | null>;
}
```

The exact interface can be extended when required.

The important requirement is:

The rest of the application must communicate with standardized internal interfaces, NOT directly with provider-specific APIs.

# 6. INTERNAL IDs VS EXTERNAL IDs

This is a CRITICAL requirement.

Every entity must have an internal database ID.

Never use an external API ID as our primary internal ID.

Example:

```text
Internal Team ID:
15

TheSportsDB:
86

Football Provider B:
12345

Provider C:
998
```

Create provider mapping records.

Example concept:

```text
ExternalEntityMapping

internalEntityId
provider
externalId
entityType
```

The same concept must work for:

* Teams
* Players
* Leagues
* Matches
* Countries
* Seasons

Never assume that two providers use the same IDs.

---

# 7. ENTITY NORMALIZATION

Different providers may return:

```text
Real Madrid
Real Madrid CF
Real Madrid Club de Fútbol
```

These must be resolved to the same internal Team.

Use:

* Provider external IDs
* Internal IDs
* Normalized names
* Aliases
* Country
* League
* Season
* Other identifiers when available

Do NOT rely only on fuzzy name matching.

If automatic matching is uncertain, flag it instead of creating duplicate entities.

---

# 8. DATA SOURCE PRIORITY

Create a configurable provider priority system.

Example:

```text
Matches:

Primary Provider
↓
Secondary Provider
↓
Fallback Provider
↓
Cache
```

Do not hard-code the priority throughout the application.

Create a central configuration/service where provider priorities can be changed.

Example:

```text
MATCHES:
1. Provider A
2. Provider B
3. Provider C

LINEUPS:
1. Provider B
2. Provider A

NEWS:
1. GNews
2. NewsData
3. RSS
```

These are examples only and must remain configurable.

---

# 9. API FAILURE HANDLING

If one provider fails:

DO NOT crash the application.

Handle:

* Timeout
* HTTP errors
* Rate limits
* Invalid responses
* Empty responses
* Authentication errors
* Temporary provider downtime

Use fallback providers when available.

Use cached data when appropriate.

---

# 10. RATE LIMIT PROTECTION

Implement:

* Request caching
* Request deduplication
* Retry logic
* Exponential backoff
* Timeouts
* Rate-limit detection
* Provider health tracking

Example:

100 users request the same match.

Do NOT send 100 requests to the external provider.

Instead:

```text
1 external request
↓
cache
↓
100 users receive the shared result
```

---

# 11. CACHE ARCHITECTURE

Create a cache abstraction.

Do not tightly couple business logic to Redis.

Example:

```typescript
interface CacheService {
  get<T>(key: string): Promise<T | null>;
  set<T>(key: string, value: T, ttl: number): Promise<void>;
  delete(key: string): Promise<void>;
}
```

This allows Redis or another cache provider to be changed later.

# 24. DO NOT DO THESE THINGS

Do NOT:

* Build a static fake football application.
* Hard-code football data into components.
* Call external APIs directly from the frontend.
* Use external API IDs as internal primary IDs.
* Assume all providers use the same IDs.
* Duplicate teams because names differ.
* Invent unavailable statistics.
* Invent xG.
* Make fake lineups appear as real data.
* Put API keys in frontend code.
* Hard-code one API provider throughout the application.
* Create unnecessary dependencies.
* Build every feature before the foundation is tested.
